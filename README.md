# Sisili General Supplies — website

Static website for Sisili General Supplies, an agricultural and general supply company in
Nairobi. Built from the `Sisili Website.dc.html` design prototype and the `Sisili Brand System`
specification.

Plain HTML, CSS and JavaScript generated by a zero-dependency Node build script. No framework,
no runtime dependencies, no CMS.

**`npm run build` produces `dist/` as nothing but flat `.html` files** (plus `robots.txt` and
`sitemap.xml`) — no subfolders, no `assets/` directory, no build scripts, no `package.json`.
Every page has its CSS and JavaScript folded directly in and the favicon inlined as a data URI,
so there is nothing else for a page to load. `dist/` is the entire deliverable: drag that one
folder into Vercel, or open `dist/index.html` straight from disk and the whole site works with
no server.

A `--linked` build is also available if you'd rather deploy the conventional way — directory-per-
page clean URLs (`/supplies/`) with one shared, cacheable `styles.css` and `app.js` in
`dist/assets/` instead of copied into every page. Neither is more "correct"; `--linked` trades
the single-folder simplicity above for smaller page sizes and cacheable assets. Vercel serves
either layout without configuration — pick `--linked` only if that trade-off matters to you.

## Quick start

```bash
npm run build          # dist/ as flat, self-contained .html files — open dist/index.html directly
npm run build:hosted    # dist/ as clean URLs + shared assets — for deploying to a real host
npm run build:root      # same clean-URL layout, written straight into the repo root — see Deployment
npm run serve           # build, then serve dist/ at http://localhost:4173
npm run dev             # same, plus rebuild on file changes
```

Node 18 or newer. There is nothing to `npm install`.

## Project structure

```
build.mjs              static site generator — routes, sitemap, robots, dev server
src/
  content.js           ALL copy and business details (start here)
  layout.js            document shell, header, footer, SEO meta, JSON-LD
  components.js        markup shared between pages
  pages/               one module per page template
  assets/              copied verbatim to the output's assets/
    styles.css         design tokens and every component style
    app.js              menu, reveal, accordions, quote form
dist/                  build output for npm run build / build:hosted — gitignored, deploy this
```

`npm run build:root` is the exception to "`dist/` is the build output" — it writes the same
`--linked` layout straight into the repo root instead (`index.html`, `about/`, `assets/`, ...),
committed there rather than gitignored. It exists only for hosts that git-pull this repo directly
into their document root with no build step of their own — see **Deployment** below. Cleaning
before a rebuild in that mode deletes only the specific top-level names it owns (listed as
`ROOT_MANAGED_ENTRIES` in `build.mjs`), never a blind wipe of the directory, so `src/`,
`build.mjs`, `package.json` and friends are never at risk.

by directory-aware hosts, while the standalone build's `404.html` is just another flat file
(open it directly to preview it, since `file://` has no server to invoke it automatically).

## Before launch — replace the placeholders

Every unfilled business detail is written as `[SOMETHING IN SQUARE BRACKETS]` in
`src/content.js`. These render on the page with a visible highlight, and their links stay inert,
so nothing invented can ship by accident. They are also excluded from the JSON-LD structured
data, so a placeholder can never reach Google as a factual claim.

Open `src/content.js` and fill in:

- [ ] `site.origin` — the production domain (canonical URLs, sitemap, structured data)
- [ ] `site.phone` — `display` (as printed) and `raw` (as dialled, e.g. `+254712345678`)
- [ ] `site.whatsapp` — `display` and `raw` (digits only, country code first, e.g. `254712345678`)
- [ ] `site.email` — `display` and `raw`
- [ ] `site.address` — `display`, `street`, `postalCode`, `directionsUrl`
- [ ] `site.hours` — `display` plus `schema` in schema.org format (`Mo-Fr 08:00-17:00`)
- [ ] `site.registration` — company registration number and KRA PIN
- [ ] `site.paymentTerms`
- [ ] `site.social` — add entries only for accounts that exist

Then search the `src/pages/` folder for the remaining bracketed content blocks, which are
deliberately empty until the real thing exists:

- [ ] `[CLIENT TESTIMONIAL — to be added]` (home) and `[TESTIMONIAL — to be added]` (about)
- [ ] `[CLIENT LOGOS — placeholder]` (about) — only with the client's written permission

Run `npm run build` and search `dist/` for `[` to confirm none are left.

## Connecting the forms

Both the quote form and the contact enquiry form are driven by `site.formEndpoint` in
`src/content.js`.

**Left empty (the default).** Nothing is silently swallowed. The quote form validates, collects
everything, and then presents the finished request as text with *Send on WhatsApp*, *Send by
email* and *Copy the list* buttons. This is a genuinely usable day-one setup for a small
business — but no request reaches a database, and no reference number is issued.

**With an endpoint set.** The form POSTs `multipart/form-data` and expects a JSON response. If
the response contains `{ "reference": "SGS-2026-0148" }`, that reference is shown on the
confirmation screen; otherwise the confirmation appears without one. If the request fails, the
visitor falls back to the WhatsApp/email handoff rather than losing what they typed.

Fields posted by the quote form:

| Field | Notes |
| --- | --- |
| `categories` | repeated, one per selected supply line |
| `item_name`, `item_qty`, `item_unit` | repeated, one set per item row, in order |
| `attachment` | zero or more files |
| `location`, `needed_by`, `fulfilment`, `notes` | delivery details |
| `name`, `organisation`, `phone`, `email`, `whatsapp_copy` | contact details |
| `company_website` | honeypot — **if this is non-empty, discard the submission** |

Server-side work still to do, per the brand specification: virus-scan uploads, rate-limit by IP,
store the row, email the sourcing desk, and send an auto-acknowledgement carrying the reference
number.

## Photography

Real photos are in place for all nine categories, the home hero, and the About page store shot —
`assets/images/*.jpg`. Each was resized to 1600px max width and compressed to ~140–350KB
(originals were 2.5–5MB straight off a camera/phone). The raw, unprocessed uploads are kept in
`originals/` at the project root, outside `assets/`, so the build never picks them up and they
never ship — that folder is just an archive in case a photo needs to be re-cropped later.

| File | Used on |
| --- | --- |
| `hero-loading.jpg` | Home hero |
| `store-interior.jpg` | About page |
| `<category-slug>.jpg` (× 9) | That category's tile on Home, its card on `/supplies/`, and its own page's hero — one file, three placements, via `shot()` in `src/components.js` |

**To replace or add a photo:** drop a new file at `assets/images/<name>.jpg` and reference it the
same way — `<img src="/assets/images/<name>.jpg" ...>` — root-absolute, exactly like the
existing ones. Both build modes resolve that path correctly: the hosted build serves it as a
real file at `/assets/images/`, the standalone build inlines the *path* rewrite (not the image
itself — photos are too large to inline without bloating every page) so it lands at flat
`images/<name>.jpg` alongside the page. Resize new photos before adding them —
`scripts/resize-images.ps1` isn't included, but any resize to ≤1600px wide at ~75–80% JPEG
quality keeps pages within the brand spec's page-weight budget (hero 180KB, page total 1MB on
3G/4G mobile). Alt text lives in `src/content.js` as `shotAlt` per category, or inline on the
`<img>` for the hero/about photos.

**One quality note:** the certified-seed-seedlings photo (a styled seed-tin display in a garden)
reads differently from the other eight, which are all real yard/store documentary shots — worth
swapping if a more consistent photo turns up later, but left in since it's still an accurate,
on-topic shot of seed packets.

The one placeholder still in place on purpose: the "Static map image" block on `/contact/` —
none of the supplied photos is a map, and a real one needs an actual Maps embed or static-map
API key, not just an image file.

## Known deviations from the specification

Three points where the delivered site differs from the brand system's build notes, each
deliberate:

1. **Fonts are loaded from Google Fonts, not self-hosted.** The specification calls for
   self-hosted woff2 subsets with no runtime Google call. To switch: download Archivo and
   IBM Plex Sans/Mono, put the woff2 files in `assets/fonts/`, replace the two
   `fonts.googleapis.com` tags in `src/layout.js` with `@font-face` rules using
   `font-display: swap`. This is the single largest remaining performance win.

2. **The mobile quote summary sits below the form, not above it.** The specification asks for a
   compact summary bar above the form on tablet. Rendered full-height above the fields it pushed
   the first question off the screen, so the form leads and the summary follows.

3. **Category item lists no longer repeat the pack size on every row.** The prototype showed the
   category's pack size against each item, which meant the same string six times. Pack sizes
   appear once, in the fact card directly above the list.

Everything else follows the specification: the token set, the type scale, the 900px navigation
collapse, mobile 2-up categories with descriptions hidden, the industries snap rail, the "why"
accordion, the vertical step timeline, footer accordions, the sticky action bar (never a
floating bubble), one 320ms reveal that respects `prefers-reduced-motion`, semantic landmarks,
one `<h1>` per page, a 3px focus ring, 44px minimum targets and `aria-live` form errors.

## Deployment

For a real host, build with `npm run build:hosted` (`node build.mjs --linked`) rather than the
plain-file default — it produces clean URLs (`/supplies/`) and a shared, cacheable stylesheet
and script instead of copying them into every page.

- **Vercel** — `vercel.json` sets `buildCommand: npm run build:hosted` and
  `outputDirectory: dist`, so Vercel builds it fresh on every deploy. `dist/` doesn't need to be
  committed for this path.
- **Netlify / Cloudflare Pages / GitHub Pages** — build command `npm run build:hosted`, publish
  directory `dist`.
- **cPanel / shared hosting, manual upload** — upload the contents of `dist/` into `public_html`.
- **cPanel Git Version Control, repository path *is* the document root (e.g. HostAfrica)** — see
  below. `npm run build:root` instead of `build:hosted`.

The directory-per-page layout means clean URLs work everywhere without rewrite rules. Set
`site.origin` before building so the canonical URLs and sitemap point at the real domain.

### HostAfrica (cPanel Git Version Control)

HostAfrica's cPanel Git Version Control is configured with the repository path set directly to
the domain's document root
(`~/domains/sisilisupplies.co.ke/public_html/`) — there's no separate clone location and no
Node.js to run a build on pull. So the generated site has to already be real files sitting at the
*top* of the repo when cPanel pulls it, which is exactly what `npm run build:root`
(`node build.mjs --root`) produces: `index.html`, `about/`, `assets/`, etc. written straight into
the repo root, alongside (not replacing) `src/`, `build.mjs`, `package.json` and the rest of the
source.

This is kept in sync automatically by `.github/workflows/build-dist.yml`: every push to `main`
rebuilds with `--root` and, if anything changed, commits it straight back with `[skip build]` in
the message (which the workflow checks for, so it doesn't trigger itself in a loop). So day to
day: edit `src/content.js` or whatever, push to `main`, wait for the Action to commit the
rebuilt output, then pull in cPanel — no deployment task needed, since the repo root already *is*
the document root.

Two things worth knowing:

- The build only deletes the specific top-level names it generates (`index.html`, `about/`,
  `assets/`, etc. — the full list is `ROOT_MANAGED_ENTRIES` in `build.mjs`), never the whole
  directory, so source and tooling files are never at risk even though they live side by side
  with the generated output.
- Source and tooling files (`build.mjs`, `src/`, `package.json`, `README.md`, `.github/`) end up
  readable at the live domain (e.g. `sisilisupplies.co.ke/build.mjs`) since they sit in the same
  directory the web server serves from. Nothing in them is secret, but if that ever changes, it
  needs a real `Repository Path` outside `public_html` plus a `.cpanel.yml` deployment task to
  copy the build output across instead.
